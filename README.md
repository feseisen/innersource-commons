# innersource-commons — 作り手が報われる共有の仕組み

いいものを作った人の成果を、他の人がそのまま使い回せる状態を組織の中に作るための設計。

一般名は**インナーソース（InnerSource）** — OSS のやり方を組織内部に持ち込む実践です。

---

## 出発点

発端は言葉探しでした。

> 「無償で共有して、それを他の人が使ってさらにいいものを作る文化を、何と呼べばいいか」

ニコニ・コモンズや MMD の素材配布文化のような、**作った人のクレジットが残ったまま二次利用が回っていく**あの状態です。「コモンズ」という語に行き着き、そこから「これを組織の中に作りたい」に展開しました。

## 設計の中心 — 効率ではなく、作り手が報われること

車輪の再発明を避ける・無駄を減らす、という効率の話から入りますが、**中心に置いているのは評価の方**です。

> 「ちゃんと作った人の手柄になってほしい。いけてるものを作った人ってちゃんと評価されてほしい」

**これは機能の取捨に直結します。** 迷ったら「**帰属と評価が成立するか**」を先に見る、という判断順序になります。効率だけで設計すると、作り手の名前が消えた「共有フォルダ」に着地します。それは作りたいものではありません。

### 無償を前提にしない

**共有＝タダ、という思い込みを持たない。** 有償・費用配賦もあり得ます。
「無償で共有して」という最初の言い方は、後から自分で「無償が当然ではないですね」と言い直しました。

## 最大の設計上の分岐 — 順位をつけない

ここが一番難しく、一番重要な判断です。

> 「競争させたいんじゃなくて、単に作った人がちゃんと評価されてほしいみたいな、そういう価値観なので、**逆に不利益になるようなことも避けたい**」
>
> 「とはいえ、その作られたものが**どれだけ高く評価されているかとか、どう人気なのかみたいな話は、情報としてとても有用**だと思うんですよね」

**この2つを別のものとして扱います。**

| やること | やらないこと |
|---|---|
| 「最近よく使われている素材」を**探す側**に見せる | 作り手を順位で**並べる** |
| 「定番」を示して探す負担を減らす | 貢献度ランキングを出す |
| 使った実績から「あなたへのおすすめ」を出す | 作り手同士を競争させる |

**同じ人気データを、探す側のためだけに使う。** 作り手の側からは順位が見えない。

**これが二律背反になるリスクは自覚しています。** 「よく使われている」を表示した時点で、裏返せば「使われていない」が分かってしまう。完全に分離できるかは、設計で詰める必要があります。**未解決の論点として明示しておきます。**

## 使うのは素人

実物を触ったうえで出てきた要求です。

- **ターミナルで質問に答える形は分かりづらい**
- **フォルダを特定のファイルにドロップする形も分かりづらい**
- **操作は画面で完結させる**

ここで重要なのは、**作る側と使う側を分けて考える**という点です。

| | 作る側 | 使う側 |
|---|---|---|
| 誰 | 仕組みを組み立てて配る人 | ボタンを押すだけの人 |
| スキル | ある程度必要 | **前提にできない** |
| 想定 | 少数 | 大多数 |

作れる人がいることと、使う人が同じように扱えることは**別問題**です。手順書も画面設計も、この2つを分けて用意します。

## サーバーを立てられない前提で設計する

多くの組織では、自前でサーバーを立てられません。**この前提があるかないかで設計が根本的に変わります。**

そのため、本命は**既存の SaaS 基盤（SharePoint 系のドキュメント基盤＋ローコードのアプリ／ワークフロー）** の上で成立させる構成としています。

- **本命**: SaaS 基盤の上に載せる構成
- **試作・予備**: 共有ドライブ上で動く軽量版

共有ドライブ版は実際に動かして「イメージがつく」ところまで確認しました。**先に実物を触ってから本命の設計を見直す**という順序を取っています。

## 前提として確定していること

- **配布の土台は共有ドライブと社内ポータルのみ。** バージョン管理基盤（Git のような）は前提にできない
- **最初に載せるのは非コード資産。** デザイン・資料のテンプレートから始める。コードの共有はその後

**コードから始めない**のが肝です。インナーソースの文献はコード資産を前提にしているものが多いのですが、多くの組織で最初に再発明されているのは**資料とテンプレート**の方です。

## 未解決の論点

正直に残しておきます。

1. **人気の表示と、作り手への不利益の分離。** 上述のとおり完全には分離できていない
2. **所有者が利用履歴を読めることを、組織として許すか。** 帰属と評価のためには「誰が使ったか」の情報が要るが、それは利用者の側から見れば監視になりうる。**これは技術ではなく組織の判断**
3. **投稿の質の担保。** 誰でも出せる状態と、使う側が信用できる状態をどう両立するか

## この設計の位置づけ

これは特定の組織の内部システムの設計ではなく、**「サーバーを立てられない組織で、作り手が報われる共有をどう作るか」という一般的な問題への回答**として書いています。

同じ制約下にいる人の役に立てば幸いです。
